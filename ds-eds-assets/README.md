# @ac-brandsframework/eds-assets-dekker

DS-sourced assets for the EDS blocks of the dekker-lib brand, one per component (dekker-block-news, dekker-block-products, dekker-block-teaser-news, dekker-button, dekker-download, dekker-header, dekker-hero, dekker-hero-carousel, dekker-key-specs, dekker-navigation, dekker-news-card, dekker-product-card, dekker-product-teaser, dekker-product-teaser-carousel, dekker-search, dekker-table, dekker-tabs, dekker-teaser-card, dekker-teaser-link, dekker-teaser-news, dekker-text, dekker-title, dekker-top-bar): compiled DOM-build render JS, cascade-safe CSS, option lists and the brand's own globals and grid CSS. This package is generated by its own build script -- do not hand-edit anything under it; re-run the build instead.

## Field models

The package ships no field models and no field reader. A consuming site owns the fields of its blocks and reads each authored row by the name of its field.

## Option lists

`options/<component>.js` holds the choices a component offers for a property, as plain data: `export const <list> = [{ value, label }, ...]`. `value` is the CSS class (several classes are space separated) or the plain value the component takes; `label` is a display name. The empty "none" choice is not in a list, so a consumer decides whether to add it and what to call it. The files import nothing and use no `document` or `window`, so they load in Node and in the browser. `common.js` holds lists several components share. The build checks each list against the TypeScript type that defines its values, and checks that every class is defined in the shipped CSS. `import { buttonTheme } from "<path-to-this-package>/options/button.js"`, or by package name: `@ac-brandsframework/eds-assets-dekker/options/button.js`.

## Getting this into your site

This package is consumed from `node_modules` by a build step: your site's build resolves `@ac-brandsframework/eds-assets/...` and bundles or places the files your blocks import. Every file the blocks need, including the EDS runtime glue in `js/vendor/`, is in the package, so a site reads nothing from another repo. The package ships no copy script or installer.

Two more things every consumer needs, both easy to miss because nothing enforces them at import time:

1. **Load `css/foundational.css` once, globally** -- it carries structural, base and brand-theming CSS every component in this package depends on, separately from the one per-component bundle (e.g. `css/bundles/ac-card.css`) each block loads for itself. Loading only the per-component bundle renders an unstyled card.
2. **Add the brand ancestor class** -- the theming rules in `foundational.css` are scoped under a `.ds-atlascopco` (or equivalent `.ac-core`) ancestor selector, not applied globally. An element high enough up your page -- typically `<body>` or a top-level layout wrapper -- needs one of those classes, or none of the theming in `foundational.css` will match anything.

## Usage


A minimal `decorate(block)` for a block of this package copies the package's files into the site, loads `css/foundational/dekker-lib.css` once and the block's own `css/bundles/<block>.css`, reads the block's authored rows by field name, calls the component's render function from `js/<name>.js` (dekker-block-news, dekker-block-products, dekker-block-teaser-news, dekker-button, dekker-download, dekker-header, dekker-hero, dekker-hero-carousel, dekker-key-specs, dekker-navigation, dekker-news-card, dekker-product-card, dekker-product-teaser, dekker-product-teaser-carousel, dekker-search, dekker-table, dekker-tabs, dekker-teaser-card, dekker-teaser-link, dekker-teaser-news, dekker-text, dekker-title, dekker-top-bar), and carries the Universal Editor attributes onto the rendered elements with `moveInstrumentation` from `js/vendor/move-instrumentation.js`. A style field is a CSS class on the rendered element: its choices come from the package's `options/` files.
